# MergeWitness

**Replay an interaction. Check what a repair keeps.**

MergeWitness is an early-stage independent MIT-licensed project for technical leads of small Node teams. It compares a caller-authored sequence of operations across Git revisions and checks a candidate repair against frozen, explicitly declared requirements from both changes.

## The problem we are testing

Changes can pass their ordinary tests separately and together, while a particular operation sequence exposes a stateful interaction. A repair may remove that symptom by removing functionality the team still needs. Reviewers need an inspectable account of the sequence, observations and retained checks.

## What exists

The 0.3.0 local release candidate provides a CLI, a four-operation stdio MCP interface, version 2 JSON evidence and an offline HTML reader. The exact accepted tarball is available through [mergewitness.com.br](https://mergewitness.com.br/), together with installation instructions, recorded reports and a two-minute product film. There is no public npm release or independent public GitHub repository yet. Internal technical checks do not establish customer adoption or universal repair guarantees.

The reproducible tenant-pricing/cache example is synthetic. Its supplied demo repair is identified as supplied. A separate user-forwarded Claude proposal was checked locally. Public incident replays are known cases, not a blind benchmark. [QuietClash](https://github.com/arbade/quietclash) and [mumei](https://github.com/iroha924/mumei) overlap with this direction; originality and superiority are not established.

## First customer hypothesis and offer

A technical lead with a recent, repeatable stateful interaction in a trusted Node repository. The first integration pilot is free and limited to one repository, one case and up to two technical sessions. The team retains its source and merge decision. Only reviewed, trusted code is eligible; subprocesses and worktrees are not hardened sandboxes.

The commercial hypothesis is an open MIT core with paid integration and maintenance help if repeated demand appears. Pricing, willingness to pay and recurring demand have not been validated. No hosted execution service is offered.

## Claude proposes; local checks evaluate

An optional model can suggest a candidate while MergeWitness retains the declared checks and execution evidence. The founder obtained one proposal through free Claude web and forwarded the complete response. A local controller applied the unchanged module, verified it and verified the same code in a fresh analysis. Provider identity is user-reported; the provider interface/model were not independently captured. A model-mediated Claude Code/MCP integration is not claimed. See the [recorded example](https://mergewitness.com.br/claude-web-workflow.html).

## Evidence we need next

The next step is to invite outside developers to test comprehension and reproduction, then investigate one consented real case. Internal learning targets are three unaided reproductions in roughly ten minutes and two concrete returns after 7–14 days. Assisted attempts, failures and missing follow-ups will be recorded.

External pilots, customers, revenue and recurring demand have not been demonstrated.
